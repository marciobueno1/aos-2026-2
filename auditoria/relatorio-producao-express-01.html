S1 🔴 Admin com senha padrão + "apagar banco" sem trava em produção

Onde: seeder e index.js

O problema: o seeder cria o admin rwieruch com a senha fixa password123 publicada no GitHub, e nos testes iniciais essa senha autenticou no banco Neon. Se alguém ainda copiar ERASE_DATABASE_ON_SYNC=true para produção por engano, a API apaga as tabelas (sync({ force: true })) e recria esse mesmo admin público.

🚨 Cuidado

Credenciais padrão lideram incidentes reais (OWASP Top 10 A07 – Falhas de Identificação e Autenticação) e são o primeiro alvo de scanners automáticos.

Como corrigir:

  1. Troque ou apague a conta rwieruch no banco imediatamente.
  2. Leia as senhas do seed via variável de ambiente, sem string fixa no código:
js
// seeders/20261114000001-initial-users-with-messages.js
const adminPassword = process.env.SEED_ADMIN_PASSWORD;
if (!adminPassword || adminPassword.length < 12) {
  throw new Error("Defina SEED_ADMIN_PASSWORD (mín. 12 caracteres) para rodar o seed.");
}
  1. Bloqueie ERASE_DATABASE_ON_SYNC=true em produção direto no env.js (.refine()):
js
// src/index.js (ou via Zod .refine no env.js)
if (eraseDatabaseOnSync && env.NODE_ENV === "production") {
  console.error("❌ ERASE_DATABASE_ON_SYNC=true não é permitido em produção.");
  process.exit(1);
}

S2 🔴 Rate limit burlável e que não funciona com várias instâncias

Onde: index.js:21 (trust proxy) e rateLimiter.js

Parte 1 – IP falsificado: o limitador usa req.ip. Com app.set("trust proxy", 1), o Express aceita o cabeçalho X-Forwarded-For enviado pelo cliente. Atrás de exatamente 1 proxy confiável (como a Vercel), a borda sobrescreve esse cabeçalho. Em uma VM direta, container sem proxy ou atrás de 2 proxies (ex.: Cloudflare + Nginx), o cliente inventa o próprio IP e zera o bloqueio:

bash
# Cada requisição "vem" de um IP diferente → o limitador nunca bloqueia
for i in $(seq 1 1000); do
  curl -s -X POST http://api/session \
    -H "X-Forwarded-For: 10.0.0.$i" \
    -H "Content-Type: application/json" \
    -d '{"login":"admin","password":"tentativa'$i'"}'
done

Nos testes locais sem proxy, 12 senhas erradas passaram sem bloqueio e 110 chamadas burlaram a cota global de 100.

Parte 2 – memória local: o express-rate-limit usa MemoryStore. Em clusters ou funções serverless com N instâncias simultâneas, o limite real se multiplica por N e reinicia a cada cold start.

Parte 3 – apenas por IP: uma botnet com vários IPs consegue atacar a mesma conta sem disparar o teto por endereço IP.

Como corrigir:

js
// src/utils/env.js – configurável por ambiente
TRUST_PROXY: z.coerce.number().int().min(0).default(0),

// src/index.js
app.set("trust proxy", env.TRUST_PROXY); // Vercel/Render: 1 · VM sem proxy: 0
js
// src/middlewares/rateLimiter.js
import rateLimit from "express-rate-limit";
import { RedisStore } from "rate-limit-redis";
import { redisClient } from "../utils/redis.js";

const store = new RedisStore({
  sendCommand: (...args) => redisClient.sendCommand(args),
});

export const limiterMiddleware = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 100,
  store,
  standardHeaders: "draft-7",
  legacyHeaders: false,
});

// Limite por conta (independe do IP do atacante)
export const loginPerAccountLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 10,
  store,
  keyGenerator: (req) =>
    `login:${String(req.body?.login ?? "").trim().toLowerCase()}`,
  skipSuccessfulRequests: true,
});
💡 Dica

Em empresas, WAF/CDN (Cloudflare, AWS WAF, Vercel Firewall) segura volumetricamente na borda; o rate limit em Redis protege regras de negócio como login e cadastro.

S3 🟠 Troca de senha/e-mail sem senha atual; token antigo segue válido

Onde: userController.js, userService.js, auth.js

O problema: com um access token capturado (válido por 15 minutos), alguém consegue chamar PUT /users/:id enviando { "password": "nova" } sem confirmar a senha atual — ou trocar o e-mail para assumir o "esqueci minha senha". Na situação inversa, quando a vítima troca a própria senha, os refresh tokens são revogados (👍), mas o access token roubado continua respondendo 200 até expirar.

Como corrigir:

  1. Exigir currentPassword quando o titular alterar senha ou e-mail:
js
// validationSchemas.js – updateUserSchema
currentPassword: z.string().min(1).optional(),

// userService.updateUser
const isSelf = actor?.id === id;
if (isSelf && (password !== undefined || email !== undefined)) {
  if (!currentPassword || !(await user.validatePassword(currentPassword))) {
    throw new AppError("Senha atual incorreta.", 401);
  }
}
  1. Invalidar JWTs antigos com tokenVersion (sem custo extra, pois o authMiddleware já consulta o usuário no banco):
js
// models/user.js
tokenVersion: { type: DataTypes.INTEGER, allowNull: false, defaultValue: 0 },

// sessionService.createAccessToken
jwt.sign({ id: user.id, role: user.role, tv: user.tokenVersion }, ...)

// userService.updateUser – incrementa na troca de senha ou role
if (password !== undefined || roleChanged) {
  await user.increment("tokenVersion", { transaction: t });
}

// middlewares/auth.js
if (!user || payload.tv !== user.tokenVersion) {
  return next(new AppError("Sessão expirada. Faça login novamente.", 401));
}

S6 🟡 Username pode ser igual ao e-mail de outra pessoa; e-mail sem normalização

Onde: user.js – findByLogin, validationSchemas.js – createUserSchema

O problema: como User.findByLogin buscava primeiro por username e aceitava qualquer caractere no cadastro, um atacante registrava username = "maria@empresa.com":

Contausernameemail
Vítimamariamaria@empresa.com
Atacantemaria@empresa.comx@x.com

Ao digitar o próprio e-mail no login, a Maria caía na conta do atacante e tomava 401. Sem .toLowerCase(), Maria@Empresa.com e maria@empresa.com também viravam contas distintas.

Como corrigir:

js
// validationSchemas.js
username: z.string().trim()
  .regex(/^[a-zA-Z0-9_.-]{3,30}$/, "Use 3 a 30 caracteres: letras, números, _ . -"),
email: z.string().trim().toLowerCase().max(254).pipe(z.email("Formato de e-mail inválido")),

// models/user.js – decide pelo "@" (1 query em vez de 2)
User.findByLogin = async (login) => {
  const value = login.trim();
  return value.includes("@")
    ? User.findOne({ where: { email: value.toLowerCase() } })
    : User.findOne({ where: { username: value } });
};

S7 🟡 Enumeração de usuários

Onde: error.js, sessionService.js – authenticate

O problema: o login responde com mensagem neutra, mas existem dois vazamentos indiretos:

  1. No cadastro: tentar registrar fulano@empresa.com devolve 409 "email must be unique", confirmando que o e-mail tem conta (útil para phishing e credential stuffing).
  2. *Por tempo (timing attack):* contas inexistentes pulam o Argon2 (123ms vs 153ms no teste local).

Como corrigir:

js
// sessionService.authenticate – sempre gasta tempo equivalente de hash
const DUMMY_HASH = await argon2.hash("senha-que-ninguem-usa");

const user = await models.User.findByLogin(login);
const isValid = user
  ? await user.validatePassword(password)
  : (await argon2.verify(DUMMY_HASH, password), false);
if (!isValid) throw new AppError("Credenciais inválidas.", 401);

No cadastro, o padrão corporativo responde sempre "Verifique seu e-mail para concluir" e notifica por e-mail caso já exista conta (ou retorna erro genérico com rate limit em S5).

S8 🟡 Reuso de refresh token não derruba a sessão

Onde: sessionService.js – rotateRefreshToken

O problema: a rotação bloqueia o reuso de um refresh token já consumido (401), mas não invalida o novo token emitido. Se o atacante roubar R1, trocar por R2 e a vítima depois tentar usar R1, ela é desconectada enquanto R2 segue ativo por até 7 dias.

*Como corrigir (refresh token family):* registrar um familyId e usedAt; ao detectar envio de token já usado, revogar todos os tokens daquela família:

js
if (dbToken?.usedAt) {
  await models.RefreshToken.destroy({ where: { familyId: dbToken.familyId }, transaction: t });
  return { invalidOrExpired: true };
}

S9 🟡 Detalhes do JWT

Onde: sessionService.js:9-19, env.js:22-24, .env.sample

O problema:

  • E-mail no payload: JWT HS256 é assinado, não criptografado (jwt.io lê direto), carregando dado pessoal (LGPD) por logs e proxies.

12.2 Quiz interativo para projetar em sala

Quiz 1: Por que o ataque com X-Forwarded-For funcionou em localhost e falhou na Vercel?

Cenário: em http://localhost:4001, enviar -H "X-Forwarded-For: 10.0.0.1" permitiu 12 tentativas de login sem bloqueio. Contra https://aos-2026-2-nine.vercel.app/, o servidor ignorou o cabeçalho forjado e bloqueou pelo IP real 152.241.x.x. Por quê?

Resposta comentada: Com app.set("trust proxy", 1), o Express confia no último salto de proxy em X-Forwarded-For. Na borda da Vercel, o Edge Proxy sobrescreve/anexa o IP real da conexão TCP antes de encaminhar para a API. Em localhost (ou numa VM exposta direto na internet), não existe proxy confiável limpando o cabeçalho, então o Express aceita o IP inventado pelo cliente. Por isso trust proxy deve ser configurável por variável de ambiente (0 sem proxy, 1 atrás de 1 proxy confiável).

Quiz 2: O npm audit apontou 2 vulnerabilidades moderadas ligadas ao sequelize e sugeriu npm audit fix --force. Devemos rodar?

Cenário: após npm audit fix, críticas e altas sumiram, restando 2 alertas moderados na dependência transitiva uuid do sequelize@6.37.8. A CLI sugeriu --force, que faria downgrade para sequelize@3.30.0. O que fazer?

Resposta comentada: Nunca executar --force automaticamente. Voltar do Sequelize v6 para v3 quebraria ESM, UUIDv4, transações e validações da API inteira. Em supply chain security, primeiro verifica-se se o código realmente alcança a função vulnerável (aqui sequelize usa só geração uuid.v4(), sem parser vulnerável) para então documentar o risco aceito ou planejar upgrade controlado de versão major.

Quiz 3: Os testes unitários tinham 95,6% de cobertura e 100% de sucesso, mas uma mensagem de 500 caracteres retornou HTTP 500. Como escapou?

Cenário: tests/validationSchemas.test.js aprovava textos de 500 caracteres no Zod, mas em produção contra o PostgreSQL a requisição devolvia erro 500 (22001). O que falhou na estratégia de testes?

Resposta comentada: A suíte unitária validava o schema Zod isolado e services mockados, sem chegar ao SGBD real. No Sequelize, DataTypes.STRING sem tamanho cria VARCHAR(255), gerando divergência com o limite 1000 do Zod. A correção pede duas medidas juntas: mesma fonte de tamanho entre validação e schema (DataTypes.STRING(1000) + .max(255)) e suíte E2E/integração rodando contra PostgreSQL real.

Quiz 4: Mesmo com a senha do Neon trocada, o que aconteceria se JWT_SECRET fosse igual ao do .env.sample?

Cenário: imagine que a senha do admin no banco já foi rotacionada, mas o servidor em produção ficou com JWT_SECRET=mysupersecretpassword. Como alguém viraria ADMIN sem saber nenhuma senha?

Resposta comentada: Com o segredo HS256 conhecido (ou fraco o bastante para quebrar via hashcat), basta criar uma conta comum (POST /users), ler o userId do admin em GET /messages e assinar localmente um JWT HS256 com { id: "<id_do_admin>", role: "ADMIN" } usando "mysupersecretpassword". Como o authMiddleware valida a assinatura e carrega o usuário pelo id, o atacante assume o painel administrativo na hora. Nos testes contra a Vercel, um token forjado assim retornou 401.

Quiz 5: Por que desativar o logging padrão do Sequelize em produção e proibir @ no username?

Cenário: duas mudanças curtas do dba1d97: logging: false fora de development e .refine((val) => !val.includes("@")) no username. Que problema cada uma resolve?

Resposta comentada: (1) Com logging padrão ligado, o Sequelize joga toda cláusula WHERE no stdout, enviando e-mails e hashes de refresh tokens para agregadores de log em nuvem (CWE-532). (2) Aceitar @ no username com busca sequencial (username primeiro, depois email) permite que um atacante cadastre username = "vitima@unicap.br" e bloqueie o login da vítima quando ela tentar entrar pelo e-mail.
