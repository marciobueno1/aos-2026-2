S1 🔴 Admin com senha padrão + "apagar banco" sem trava em produção

Onde: seeder e index.js

O problema: O seeder cria o usuário rwieruch como ADMIN com a senha password123, que está escrita no código (e o código está no GitHub). Testamos e o login funciona no banco configurado. Qualquer pessoa que leia o repositório vira administrador.

Além disso, se alguém colocar ERASE_DATABASE_ON_SYNC=true no ambiente de produção (por engano, copiando o .env de dev), a aplicação apaga o banco inteiro (sync({ force: true })) e recria esse admin com senha conhecida. Não existe nenhuma trava.

🚨 Cuidado

Essa é a falha nº 1 em incidentes reais: credenciais padrão. Está no topo de listas como o OWASP Top 10 (A07 – Falhas de Identificação e Autenticação) e é exatamente o que robôs testam primeiro.

Como corrigir:

  1. Agora: troque a senha desse usuário no banco (ou apague-o).
  2. Senha do seed vem de variável de ambiente, e nunca do código:
js
// seeders/20261114000001-initial-users-with-messages.js
const adminPassword = process.env.SEED_ADMIN_PASSWORD;
if (!adminPassword || adminPassword.length < 12) {
  throw new Error("Defina SEED_ADMIN_PASSWORD (mín. 12 caracteres) para rodar o seed.");
}
  1. Trava contra apagar banco em produção:
js
// src/index.js
if (eraseDatabaseOnSync && env.NODE_ENV === "production") {
  console.error("❌ ERASE_DATABASE_ON_SYNC=true não é permitido em produção.");
  process.exit(1);
}

Dá pra colocar essa regra no próprio schema do Zod em env.js com .refine(), assim ela fica junto das outras validações de ambiente.

S2 🔴 Rate limit burlável e que não funciona com várias instâncias

Onde: index.js:21 (trust proxy) e rateLimiter.js

O problema (parte 1 – IP falsificado): O rate limit conta tentativas por IP. O IP vem de req.ip, e com app.set("trust proxy", 1) o Express acredita no cabeçalho X-Forwarded-For que o cliente manda.

Isso só é seguro se existir exatamente 1 proxy confiável na frente que sobrescreve esse cabeçalho. Se a API rodar direto numa VM, num container sem proxy, ou atrás de 2 proxies (ex.: Cloudflare + Nginx), o atacante escolhe o próprio IP:

bash
# Cada requisição "vem" de um IP diferente → o limitador nunca bloqueia
for i in $(seq 1 1000); do
  curl -s -X POST http://api/session \
    -H "X-Forwarded-For: 10.0.0.$i" \
    -H "Content-Type: application/json" \
    -d '{"login":"admin","password":"tentativa'$i'"}'
done

Foi o que fizemos no teste: 12 senhas erradas sem bloqueio e 110 requisições passando pelo limite global de 100. Ou seja, brute force e DDoS de aplicação ficam liberados.

O problema (parte 2 – memória local): O express-rate-limit guarda os contadores na memória do processo. Em produção normalmente rodam várias instâncias (ou funções serverless, como na Vercel). Cada uma tem seu próprio contador, então com 10 instâncias o limite real vira 10× maior. E a cada reinício/deploy, o contador zera.

O problema (parte 3 – só por IP): Um atacante com uma botnet (milhares de IPs) consegue testar senhas de uma mesma conta sem nunca bater no limite por IP.

Como corrigir:

js
// src/utils/env.js – deixar configurável por ambiente
TRUST_PROXY: z.coerce.number().int().min(0).default(0), // 0 = não confia em nenhum proxy

// src/index.js
app.set("trust proxy", env.TRUST_PROXY); // Vercel/Render/Heroku: 1 · VM sem proxy: 0
js
// src/middlewares/rateLimiter.js
import rateLimit, { ipKeyGenerator } from "express-rate-limit";
import { RedisStore } from "rate-limit-redis";
import { redisClient } from "../utils/redis.js";

const store = new RedisStore({
  sendCommand: (...args) => redisClient.sendCommand(args),
});

// Limite por IP (como já existe), mas com store compartilhado
export const limiterMiddleware = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 100,

  standardHeaders: "draft-7",
  legacyHeaders: false,
});

// NOVO: limite por CONTA (independe do IP do atacante)
export const loginPerAccountLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 10,
  store,
  keyGenerator: (req) =>
    `login:${String(req.body?.login ?? "").trim().toLowerCase()}`,
  skipSuccessfulRequests: true, // só conta as falhas
});
💡 Dica

Em empresas, a primeira linha contra DDoS não é o código: é um WAF/CDN na frente (Cloudflare, AWS WAF, Vercel Firewall). O rate limit da aplicação é a segunda camada, que protege regras de negócio (login, cadastro). As duas se complementam.

S3 🟠 Troca de senha/e-mail sem senha atual; token antigo segue válido

Onde: userController.js, userService.js, auth.js

O problema: Imagine que alguém roubou o access token da Alice (por XSS, Wi-Fi público, extensão maliciosa, computador emprestado). Esse token dura só 15 minutos. Mas com ele o atacante consegue:

  1. PUT /users/:id com { "password": "nova" } → 200 (não pede a senha atual).
  2. Agora ele tem a senha. A conta é dele. A Alice foi expulsa.

Ele também pode trocar o e-mail, o que num sistema com "esqueci minha senha" seria a tomada definitiva da conta.

E tem o caminho inverso: a Alice percebe e troca a senha. Os refresh tokens são revogados (👍), mas o access token roubado continua valendo até expirar (testamos: 200 depois da troca).

Como corrigir:

  1. Exigir a senha atual quando o próprio usuário troca senha ou e-mail:
js
// validationSchemas.js – updateUserSchema
currentPassword: z.string().min(1).optional(),

// userService.updateUser
const isSelf = actor?.id === id;
if (isSelf && (password !== undefined || email !== undefined)) {
  if (!currentPassword || !(await user.validatePassword(currentPassword))) {
    throw new AppError("Senha atual incorreta.", 401);
  }
}
  1. Invalidar access tokens antigos com uma "versão de token":
js
// models/user.js – novo campo
tokenVersion: { type: DataTypes.INTEGER, allowNull: false, defaultValue: 0 },

// sessionService.createAccessToken – inclui a versão no JWT
jwt.sign({ id: user.id, role: user.role, tv: user.tokenVersion }, ...)

// userService.updateUser – ao trocar senha/role: incrementa
if (password !== undefined || roleChanged) {
  await user.increment("tokenVersion", { transaction: t });
}

// middlewares/auth.js – depois de buscar o usuário no banco
if (!user || payload.tv !== user.tokenVersion) {
  return next(new AppError("Sessão expirada. Faça login novamente.", 401));
}

Como o authMiddleware já busca o usuário no banco a cada requisição, essa verificação não custa nada a mais.

S5 🟡 Rotas sensíveis sem limite próprio

Onde: routes/session.js, routes/user.js:27

O problema: o limitador mais rígido (authLimiterMiddleware, 5 tentativas) só está no POST /session. Ficaram de fora:

  • POST /users (cadastro) → dá pra criar milhares de contas falsas (spam, encher o banco).
  • POST /session/refresh → rota pública que consulta o banco.
  • PUT /users/:id com troca de senha (principalmente depois de corrigir o S3, pra ninguém fazer brute force na "senha atual").

Como corrigir: aplicar limitadores específicos nessas rotas, por exemplo:

js
router.post("/", signupLimiter, validate(createUserSchema), userController.createUser);
router.post("/refresh", refreshLimiter, validate(refreshTokenSchema), sessionController.refresh);

Em produção, também vale colocar CAPTCHA (hCaptcha, Cloudflare Turnstile) no cadastro.

S6 🟡 Username pode ser igual ao e-mail de outra pessoa; e-mail sem normalização

Onde: user.js – findByLogin, validationSchemas.js – createUserSchema

O problema: O login aceita username ou e-mail, e procura primeiro pelo username. Como o username aceita qualquer texto, um atacante pode se cadastrar com username = e-mail da vítima:

Contausernameemail
Vítimamariamaria@empresa.com
Atacantemaria@empresa.comx@x.com

Quando a Maria digita maria@empresa.com no login, o sistema encontra a conta do atacante (pelo username) e a senha não bate → 401. Testamos: a vítima não consegue mais logar pelo e-mail. É uma negação de serviço direcionada e, dependendo do sistema, pode virar phishing.

Bônus: o e-mail não é convertido para minúsculas, então Maria@Empresa.com e maria@empresa.com viram duas contas diferentes.

Como corrigir:

js
// validationSchemas.js

S7 🟡 Enumeração de usuários

Onde: error.js, sessionService.js – authenticate

O problema: o login responde de forma genérica (👍), mas existem outros jeitos de descobrir se um e-mail está cadastrado:

  1. Pelo cadastro: tentar cadastrar fulano@empresa.com devolve 409 "email must be unique" → o atacante sabe que a pessoa tem conta. Com isso, monta listas para phishing ou para credential stuffing (testar senhas vazadas de outros sites).
  2. *Pelo tempo de resposta (timing attack): quando o usuário não existe, o código não roda o Argon2*; quando existe, roda. Isso gera uma diferença de tempo mensurável. No nosso teste a diferença apareceu (123ms × 153ms), mas o banco remoto atrapalha a medição. Num servidor perto do banco, a diferença fica bem mais clara.

Como corrigir:

js
// sessionService.authenticate – sempre gasta o mesmo tempo
const DUMMY_HASH = await argon2.hash("senha-que-ninguem-usa"); // gerado 1x no boot

const isValid = user
  ? await user.validatePassword(password)
  : (await argon2.verify(DUMMY_HASH, password), false);

No cadastro, a solução "de verdade" é o fluxo de confirmação por e-mail: a API sempre responde "enviamos um e-mail para confirmar" e quem já tem conta recebe um aviso no e-mail, não na tela. Como paliativo: mensagem genérica ("Não foi possível concluir o cadastro") + rate limit no cadastro (S5).

S8 🟡 Reuso de refresh token não derruba a sessão

Onde: sessionService.js – rotateRefreshToken

O problema: a rotação está certa: cada refresh token só vale uma vez (testamos: reuso → 401 👍). Mas pense no cenário:

  1. O atacante rouba o refresh token R1 da vítima.
  2. O atacante usa R1 primeiro → recebe R2 (válido).
  3. A vítima tenta usar R1 → 401. Ela é deslogada e loga de novo.
  4. O atacante continua com R2 funcionando por até 7 dias.

O reuso de um token já rotacionado é um sinal claro de roubo, mas hoje ele é ignorado.

*Como corrigir (refresh token family / reuse detection): guardar os tokens usados (ou um familyId) e, quando um token já usado aparecer de novo, revogar todos os tokens daquela família/usuário*:

js
// RefreshToken: adicionar familyId (UUID) e usedAt (DATE)
if (dbToken?.usedAt) {
  // reuso detectado → derruba todas as sessões da família
  await models.RefreshToken.destroy({ where: { familyId: dbToken.familyId }, transaction: t });
  return { invalidOrExpired: true };
}

S9 🟡 Detalhes do JWT

Onde: sessionService.js:9-19, env.js:22-24, .env.sample

O problema:

  env.JWT_SECRET,

// auth.js
jwt.verify(token, env.JWT_SECRET, { algorithms: ["HS256"], issuer: "aos-api", audience: "aos-web" });

# gerar um segredo decente
openssl rand -base64 48

No .env.sample, use um placeholder óbvio: JWT_SECRET=<gere com: openssl rand -base64 48>.

B1 🟠 Validação aceita dados que não cabem no banco → erro 500

Onde: message.js:8-14, user.js:16-31, validationSchemas.js

O problema: o Zod deixa a mensagem ter até 1000 caracteres, mas no model ela é DataTypes.STRING, que no PostgreSQL vira VARCHAR(255). O mesmo vale para username e email, que não têm limite no Zod. Resultado (testado):

  • Mensagem com 500 caracteres → 500 "Algo deu errado no servidor"
  • Username com 300 caracteres → 500

Para o usuário, parece que o sistema quebrou. Para a equipe, aparece um monte de erro 500 no monitoramento que, na verdade, é erro de validação (400). E para o atacante, é um jeito barato de gerar ruído e alarmes falsos.

Regra de ouro: as regras de validação da API e as restrições do banco precisam contar a mesma história. O ideal é ter uma única fonte de verdade para os limites (ex.: constantes compartilhadas).

js
// src/utils/limits.js
export const LIMITS = { USERNAME: 30, EMAIL: 254, MESSAGE: 1000 };

text: { type: DataTypes.STRING(LIMITS.MESSAGE), allowNull: false, validate: { notEmpty: true } },
// (ou DataTypes.TEXT, se não quiser limite no banco)

// models/user.js
username: { type: DataTypes.STRING(LIMITS.USERNAME), ... },
email:    { type: DataTypes.STRING(LIMITS.EMAIL), ... },

// validationSchemas.js
text: z.string().trim().min(1).max(LIMITS.MESSAGE),

E, como rede de segurança, tratar o erro 22001 (string data right truncation) do PostgreSQL no errorMiddleware como 400.

B2 🟠 sequelize.sync() em vez de migrations; erro na inicialização não tratado

Onde: index.js:50-67

O problema:

  • O esquema do banco é criado com sequelize.sync(). Em produção, isso é perigoso: o sync() não sabe evoluir uma tabela que já tem dados (renomear coluna, mudar tipo, criar índice) e o sync({ force: true }) apaga tudo. Também não fica registrado o que mudou no banco e quando. Por exemplo: para corrigir o B1 num banco com dados, você vai precisar de uma migration.

Como corrigir:

  • Usar migrations versionadas (sequelize-cli ou umzug) e rodar no pipeline de deploy: npx sequelize-cli db:migrate.
  • Deixar o sync() só para desenvolvimento/testes.
  • Testar a conexão antes de subir:

const start = async () => {
  try {
    await sequelize.authenticate();
    if (syncDatabase && env.NODE_ENV !== "production") {

B3 🟡 Sem health check e sem desligamento gracioso

Onde: index.js

O problema:

  • GET / responde "Servidor express executando..." mesmo que o banco esteja fora do ar. Orquestradores (Kubernetes, ECS, Render, load balancers) usam um endpoint de saúde para decidir se mandam tráfego para a instância. Se ele mente, o usuário recebe erro.
  • Quando o servidor recebe SIGTERM (todo deploy faz isso), o processo morre na hora: requisições em andamento são cortadas e conexões com o banco ficam penduradas.

Como corrigir:

js
// liveness: o processo está de pé?
app.get("/health/live", (req, res) => res.status(200).json({ status: "ok" }));

// readiness: está pronto para receber tráfego (banco ok)?
app.get("/health/ready", async (req, res) => {
  try {
    await sequelize.authenticate();
    res.status(200).json({ status: "ok", db: "up" });
  } catch {
    res.status(503).json({ status: "error", db: "down" });
  }
});

// graceful shutdown
const shutdown = (signal) => {
  logger.info(`${signal} recebido, encerrando...`);
  server.close(async () => {
    await sequelize.close();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 10_000).unref(); // não espera para sempre
};
process.on("SIGTERM", shutdown);
process.on("SIGINT", shutdown);

B9 🟢 Paginação por OFFSET fica lenta em páginas altas

Onde: pagination.js

O problema: a paginação está correta e protegida (👍), mas usa OFFSET. Para entregar a página 100.000, o banco lê e descarta 1 milhão de linhas. O MAX_PAGE = 1_000_000 permite que alguém peça páginas altíssimas de propósito, sobrecarregando o banco (uma forma de DoS). Além disso, o findAndCountAll faz um COUNT(*) a cada chamada, que também fica caro em tabelas grandes.

Como corrigir: para tabelas que crescem muito (como mensagens), usar paginação por cursor (keyset pagination):

sql
-- em vez de OFFSET 1000000
SELECT * FROM messages
WHERE ("createdAt", id) < (:lastCreatedAt, :lastId)
ORDER BY "createdAt" DESC, id DESC
LIMIT 20;

Com um índice em ("createdAt", id), essa consulta é rápida em qualquer página.

B10 🟢 Pequenos ajustes

  • express.urlencoded({ extended: true }) (index.js:28): a API só usa JSON. O parser de formulário com extended: true aceita objetos aninhados (a[b][c]=1) e aumenta a superfície de ataque (ver a vulnerabilidade do qs no S4). Se não usa, remova.
  • Transação com um comando só (userService.deleteUser): um único DELETE já é atômico, então a transação só adiciona overhead. Vale manter se for crescer (ex.: auditoria junto).
  • Consulta ao banco em toda requisição autenticada (auth.js:75-81): é uma escolha consciente e boa para segurança (permissões valem na hora). Mas tem custo. Com muito tráfego, dá pra usar cache curto (ex.: 30s em Redis), sabendo da troca entre performance e "tempo real".
  • Mensagens de erro do Sequelize repassadas ao cliente (error.js:37-55): textos como "email must be unique" vêm em inglês e expõem nomes de colunas. Traduzir para mensagens próprias da API.

E2 🟡 Sem testes de integração; lacunas de cobertura

Onde: tests/

O problema: a cobertura de 95% impressiona, mas cobertura alta não significa que tudo foi testado. Os testes são unitários: substituem os services por funções falsas (monkey-patching, como userService.getUserById = async () => ...) e nunca sobem o servidor HTTP nem tocam num banco de verdade. Por isso, nenhum dos bugs que encontramos na prática foi pego pelos testes:

  • B1 (500 com texto longo) só aparece com banco real;
  • S2 (bypass do rate limit) só aparece com requisição HTTP real;
  • S6 (username = e-mail) só aparece com dados reais no banco.

Lacunas da cobertura atual (funções):

ArquivoFunções cobertas

Outros detalhes:

  • Arquivos como passo9.test.js e passo10.test.js são nomeados pela etapa da disciplina, não pela funcionalidade. Daqui a 6 meses, ninguém vai saber o que tem dentro. Prefira pagination.test.js, tokenRotation.test.js.
  • O monkey-patching de módulos globais pode vazar entre testes se alguém esquecer de restaurar o original.

Como corrigir: criar uma camada de testes de integração com supertest + PostgreSQL de teste (via Docker ou o service do CI):

js
// tests/integration/auth.int.test.js
import { test, before } from "node:test";
import assert from "node:assert/strict";
import request from "supertest";
import app from "../../src/app.js"; // separar app (export) de server (listen)
import { sequelize } from "../../src/models/index.js";

before(async () => { await sequelize.sync({ force: true }); });

test("mensagem com 1000 caracteres é aceita (validação = banco)", async () => {
  // ... cria usuário, faz login, envia mensagem
  const res = await request(app).post("/messages").set("Authorization", `Bearer ${token}`)
    .send({ text: "x".repeat(1000) });
  assert.equal(res.status, 201);
});

test("username não pode ser um e-mail", async () => {
  const res = await request(app).post("/users")
    .send({ username: "a@b.com", email: "c@d.com", password: "senhaForte123" });
  assert.equal(res.status, 400);
});
💡 Dica

Separe app.js (cria e exporta o Express) de server.js (faz o listen e conecta no banco). Assim os testes importam o app sem subir servidor nem rodar sync. Isso é padrão em projetos Express profissionais.

11.2 Detalhamento das Correções e Provas Reais

1) S1 — Seeder com Fallback CSPRNG + Bloqueio de Wipe em Produção

  • Antes: seeder trazia "password123" e "password456" fixas no Git; env.js aceitava ERASE_DATABASE_ON_SYNC=true com NODE_ENV=production.
  • Depois (dba1d97):
  • ADMIN_PASSWORD e USER_PASSWORD validadas como opcionais (7 a 42 caracteres) em envSchema, além de .refine(...) que aborta o startup se NODE_ENV === "production" && ERASE_DATABASE_ON_SYNC === "true".
  • No seeder, resolveSeedPassword gera crypto.randomBytes(24).toString("base64") (32 caracteres Base64 = 192 bits de entropia) quando a variável não está definida — exibindo a senha gerada via logger.warn somente com NODE_ENV=development e omitindo o segredo em produção, testes e CI sem NODE_ENV (CWE-532).
  • No banco Neon, ambas as contas (rwieruch e ddavids) tiveram suas senhas rotacionadas via tarefas/rotate-admin-password.mjs com armazenamento local restrito (0600).

3) S4 — Por que npm audit fix (sem --force) em vez de --force

  • Rodamos npm audit fix em express-01/: todas as críticas (proxy-addr) e altas (body-parser, brace-expansion) desapareceram.
  • Restaram 2 vulnerabilidades moderadas em produção (uuid < 11.1.1, dependência transitiva do sequelize@6). O npm audit sugere npm audit fix --force, que faria downgrade do sequelize da versão 6.37.8 para 3.30.0 — quebrando o projeto inteiro!
  • Lição para a aula: Nunca execute --force automaticamente; avalie sempre se a vulnerabilidade transitiva é realmente explorável no seu uso (uuid.v4() do Sequelize 6) e se a correção traz breaking changes.

4) S6 — Bloqueio de @ no username + Lookup Determinístico

  • Antes: User.findByLogin fazia duas queries sequenciais (username e depois email), permitindo que um atacante registrasse username = "vitima@email.com".
  • Depois (dba1d97): usernameSchema rejeita @ via .refine((val) => !val.includes("@")), emailSchema aplica .trim().toLowerCase(), e User.findByLogin decide pelo @:
javascript
// express-01/src/models/user.js
User.findByLogin = async (login) => {
  if (typeof login !== "string") return null;
  const normalizedLogin = login.trim();
  if (!normalizedLogin) return null;

  return normalizedLogin.includes("@")
    ? await User.findOne({ where: { email: normalizedLogin.toLowerCase() } })
    : await User.findOne({ where: { username: normalizedLogin } });
};

5) B1 — Alinhamento Zod × Banco + Erro 22001

  • Antes: Zod aceitava 1000 chars em Message.text e comprimento ilimitado em username/email, enquanto o banco possuía VARCHAR(255), gerando HTTP 500.
  • Depois (dba1d97): Message.text atualizado para DataTypes.STRING(1000) no modelo e via ALTER TABLE "messages" ALTER COLUMN "text" TYPE VARCHAR(1000); no Neon; .max(255) aplicado em usernameSchema e emailSchema; e errorMiddleware captura o código PostgreSQL 22001 retornando HTTP 400.

6) B7 — Silenciamento de Logs SQL em Produção

  • Antes: new Sequelize(databaseUrl, { dialect: "postgres", dialectModule: pg }) imprimia todo SQL no console, expondo e-mails e hashes SHA-256 em cláusulas WHERE.
  • Depois (dba1d97): logging: process.env.NODE_ENV === "development" ? console.log : false em src/models/index.js.

12.2 Quiz Interativo para Projetar em Sala

Quiz 1: Por que o ataque com X-Forwarded-For funcionou em localhost e falhou na Vercel?

Cenário: Em localhost, enviar -H "X-Forwarded-For: 10.0.0.1" permitiu fazer 12 tentativas de login sem bloqueio 429. Na Vercel (https://aos-2026-2-nine.vercel.app/), o mesmo cabeçalho foi ignorado e o servidor enxergou o IP verdadeiro 152.241.x.x. Por quê?

Resposta comentada: Com app.set("trust proxy", 1), o Express confia no último salto de proxy registrado no X-Forwarded-For. Na Vercel, a borda (Edge Proxy) sobrescreve/anexa de forma confiável o IP real da conexão TCP antes de encaminhar para a função Express. Já em localhost (ou numa VM exposta diretamente na internet sem proxy na frente), não existe nenhum proxy confiável removendo cabeçalhos falsos, então o Express aceita literalmente o IP inventado pelo atacante! Regra de ouro: trust proxy deve ser configurado por variável de ambiente (0 quando exposto direto, 1 atrás de exatamente 1 proxy confiável).

Quiz 2: O npm audit acusou 2 vulnerabilidades moderadas no sequelize e sugeriu npm audit fix --force. Devemos rodar?

Cenário: Após npm audit fix, todas as vulnerabilidades críticas e altas sumiram, sobrando apenas 2 moderadas no pacote transitivo uuid usado pelo sequelize@6.37.8. A CLI sugeriu npm audit fix --force para baixar para sequelize@3.30.0. O que a equipe deve fazer?

Resposta comentada: Nunca rodar --force às cegas! Fazer downgrade do Sequelize v6 para v3 quebraria toda a aplicação (ESM, UUIDv4, transações, hooks e validação). Em segurança de supply chain, toda vulnerabilidade precisa de triagem: verificar se a função vulnerável é alcançável no projeto (aqui sequelize só usa uuid.v4(), sem parsing de inputs externos malformados) e documentar o risco aceito ou planejar upgrade de versão major de forma controlada (ex.: Sequelize v7 quando estável).

Quiz 3: Nossos testes unitários tinham 95,6% de cobertura e 100% de sucesso, mas o ataque de 500 caracteres devolveu HTTP 500. Como isso escapou?

Cenário: Em tests/validationSchemas.test.js, o schema Zod aprovou mensagens de 500 caracteres e rejeitou de 1001. Ainda assim, em produção contra o PostgreSQL, enviar 500 caracteres causou erro 500 (22001). Qual foi a falha na estratégia de testes?

Resposta comentada: Os testes unitários testaram o schema Zod isolado e serviços mockados, sem tocar o PostgreSQL real. No Sequelize, DataTypes.STRING sem argumento cria VARCHAR(255), criando uma divergência silenciosa entre a camada de validação (1000) e o banco (255). A lição dupla é: (1) ter uma fonte única de verdade para limites entre Zod e Models (DataTypes.STRING(1000) + .max(255)), e (2) manter testes E2E / integração contra um PostgreSQL real para validar restrições do SGBD.

Quiz 4: Mesmo após corrigir a senha no Neon, o que um atacante ainda conseguiria fazer se o JWT_SECRET fosse igual ao do .env.sample?

Cenário: Suponha que um time trocou a senha do admin no banco, mas esqueceu JWT_SECRET=mysupersecretpassword no .env de produção. Como alguém viraria ADMIN em 3 requisições sem saber a senha de ninguém?

Resposta comentada: Com o segredo do JWT conhecido (ou fraco o suficiente para quebrar offline via hashcat), o atacante: (1) cria uma conta comum (POST /users); (2) consulta GET /messages autenticado e lê o userId de uma mensagem publicada pelo admin; (3) assina localmente um JWT HS256 com { id: "<id_do_admin>", role: "ADMIN" } usando "mysupersecretpassword". Como o authMiddleware confia na assinatura válida e carrega o usuário pelo payload.id, o atacante assume imediatamente a sessão do administrador! Por isso testamos explicitamente a API na Vercel contra esse segredo e confirmamos que ela rejeitou com 401.

Quiz 5: Por que desativar o logging padrão do Sequelize em produção e por que proibir @ no username?

Cenário: Duas mudanças pequenas do commit dba1d97: logging: false fora de development e .refine((val) => !val.includes("@")) no username. Que ataques ou vazamentos específicos cada uma previne?

Resposta comentada: (1) logging padrão do Sequelize imprime toda cláusula WHERE no stdout — em provedores de nuvem esses logs vão para agregadores acessíveis a mais pessoas/ferramentas, expondo e-mails e hashes de refresh tokens (CWE-532). (2) Permitir @ no username junto com uma busca sequencial (username primeiro, depois email) permite sequestro de login por e-mail / DoS direcionado: o atacante registra username = "vitima@unicap.br" e bloqueia a vítima de entrar usando o próprio e-mail.

10. Glossário rápido

TermoO que é
Brute forceTestar milhares de senhas até acertar. Defesa: rate limit, bloqueio por conta, senhas fortes, MFA.
Credential stuffingUsar listas de e-mail/senha vazadas de outros sites, apostando que a pessoa repete a senha.
DDoS / DoSAtaque de negação de serviço: sobrecarregar o sistema até ele parar de responder. DDoS é o distribuído (vários IPs ao mesmo tempo).
Rate limitLimitar quantas requisições alguém pode fazer num período.
X-Forwarded-ForCabeçalho que proxies usam para informar o IP original do cliente. Se a aplicação confia nele sem ter um proxy na frente, o cliente pode mentir o próprio IP.
trust proxyConfiguração do Express que diz em quantos proxies ele deve confiar para descobrir o IP real.
SQL InjectionInjetar comandos SQL através de campos de entrada. Defesa: queries parametrizadas/ORM e validação.
Mass assignmentEnviar campos extras (ex.: role: "ADMIN") esperando que a API grave tudo sem filtrar.
IDORInsecure Direct Object Reference: acessar dados de outra pessoa só trocando o ID na URL.
RBACRole-Based Access Control: controle de acesso por papel (USER, ADMIN).
Escalada de privilégioUm usuário comum conseguir permissões de admin.
Enumeração de usuáriosDescobrir quais e-mails/usernames têm conta, pelas mensagens ou pelo tempo de resposta.
Timing attackDescobrir informação medindo quanto tempo o servidor leva para responder.
JWTJSON Web Token. Token assinado (não criptografado!) com informações do usuário.
alg: noneAtaque clássico em que o atacante manda um JWT "sem assinatura" esperando que o servidor aceite.
Access token / Refresh tokenO access token é curto (15 min) e vai em toda requisição. O refresh token é longo (7 dias) e serve só para pegar um novo access token.
Rotação de refresh tokenA cada uso, o refresh token antigo é invalidado e um novo é emitido.
Argon2Algoritmo de hash de senha moderno, lento de propósito, resistente a GPU.
Stack traceLista de funções/arquivos por onde o erro passou. Ótimo para debugar e péssimo de mostrar para o usuário.
CORSMecanismo do navegador que controla quais sites podem chamar sua API via JavaScript. Não protege contra curl/Postman!
CSPContent Security Policy: cabeçalho que diz de onde o navegador pode carregar scripts, estilos etc.
SRISubresource Integrity: hash no <script integrity="..."> que garante que o arquivo do CDN não foi alterado.
Supply chain attackAtaque pela cadeia de dependências: comprometer uma biblioteca ou CDN que você usa.
XSSCross-Site Scripting: injetar JavaScript numa página para roubar dados (como tokens no localStorage).
CSRFCross-Site Request Forgery: um site malicioso faz o navegador da vítima enviar requisições com os cookies dela.
WAFWeb Application Firewall: firewall que filtra tráfego HTTP malicioso antes de chegar na aplicação.
MigrationScript versionado que altera a estrutura do banco de forma controlada e reversível.
Health checkEndpoint que informa se a aplicação está viva e pronta para receber tráfego.
Graceful shutdownDesligar o servidor terminando as requisições em andamento antes de sair.
CIContinuous Integration: esteira automática que roda testes/lint a cada push.
OWASP Top 10Lista das 10 categorias de falhas de segurança web mais críticas. Leitura obrigatória: https://owasp.org/Top10/
LGPDLei Geral de Proteção de Dados (Lei 13.709/2018). Dados pessoais (como e-mail) exigem cuidado.
